MothBlast 量子ラウンドシード生成 — mode='custom' バックエンド仕様

Overview

round_circuit() の mode='custom' は、Cure-API が提供する合成QPUエンドポイントへ OpenQASM 3 回路を POST し、測定結果（counts）を受け取る汎用 REST インターフェースです。ibm_marrakesh 以降のバックエンドを Cure-API 経由で SELECT するか、ゲームデータセンター向けにカスタマイズした合成QPU を CREATE して利用できます。

エンドポイント — qpu/run

サーバー側のデフォルト QPU で回路を実行します。最もシンプルな呼び出しパターンです。

POST /qpu/run デフォルトまたは指定バックエンドで 13 量子ビット H 回路を実行し counts を返す 
from cure_oracle.round_circuit import round_circuit

r = round_circuit(
    5,
    mode="custom",
    endpoint="https://cure-api.example/qpu/run",
    api_key="cure_sk_xxxx",
)

エンドポイント — qpu/select

サーバーが保有する QPU プール（ibm_marrakesh を含む複数バックエンド）から、現在の最適機を自動 SELECT して実行します。レスポンスの backend_name で実際に使用されたバックエンドを確認できます。

POST /qpu/select QPU プールから空き・精度・レイテンシを考慮してサーバーが自動選択 
r = round_circuit(
    5,
    mode="custom",
    endpoint="https://cure-api.example/qpu/select",
    api_key="cure_sk_xxxx",
)

# サーバーが選んだバックエンド名を確認
print(r["backend"])  # → "ibm_marrakesh" / "cure_synth_v2" など
SELECT の選択基準（サーバー側実装推奨）
キュー長・平均ゲートエラー率・利用可能ショット数・地理的レイテンシを重み付けスコアで評価し、最高スコアのバックエンドを選択します。

エンドポイント — qpu/create

noise_model を渡すことでサーバーがその場で合成QPUを構築し、実行します。ゲームデータセンターやスマートコントラクト連携向けに特定のノイズ特性を持つバックエンドをカスタマーごとに提供できます。

POST /qpu/create noise_model から新規合成 QPU を生成してその場で実行。結果は証明書として記録可能 
r = round_circuit(
    5,
    mode="custom",
    endpoint="https://cure-api.example/qpu/create",
    api_key="cure_sk_xxxx",
    noise_model={
        "type":       "depolarizing",
        "error_rate": 0.005,   # 0.5% — ゲーム用途に適したノイズ強度
    },
)

Request Schema

全エンドポイント共通。Content-Type: application/json で POST します。

フィールド型説明
circuit string * OpenQASM 3 形式の 13 量子ビット H 回路（Qiskit qasm3.dumps() 出力）
shots int * 測定ショット数（1〜2000）
round_num int * ラウンド番号。サーバー側ログ・スマートコントラクトの nonce ヒントとして使用
noise_model object 合成QPUのノイズプロファイル（qpu/create で使用。他エンドポイントでは無視）

リクエスト例（raw JSON）

{
  "circuit":   "OPENQASM 3.0;\ninclude \"stdgates.inc\";\nqubit[13] q;\nbit[13] c;\nh q[0:12];\nc = measure q;",
  "shots":     500,
  "round_num": 5,
  "noise_model": { "type": "depolarizing", "error_rate": 0.005 }
}

Response Schema

フィールド型説明
counts object * 測定ヒストグラム。キーは 13 文字のビット列（MSB-first、Qiskit 準拠）、値は出現回数
backend_name string 実際に使用したバックエンド名（qpu/select 時に特に重要）
qpu_seconds float QPU 使用時間（秒）。課金・証明書記録に使用

レスポンス例

{
  "counts": {
    "0100110011111": 48,  // ← 最頻ビット列 → Round 4 証明書
    "0100110011110": 35,
    "0100110011101": 29
  },
  "backend_name": "cure_synth_depolarizing_v1",
  "qpu_seconds":  0.42
}
最頻ビット列の抽出
SDK 側が max(counts, key=counts.get) で最頻ビット列を選択し、MSB-first → LSB-first に反転して 13 ビット証明書を生成します。サーバー側でこの処理を行う必要はありません。

noise_model = {"type": "depolarizing", "error_rate": 0.02}

Extra Headers

extra_headers でゲームセッション・スマートコントラクト・ルーティング情報を HTTP ヘッダとして付加できます。

ヘッダ名（例）用途
X-Session-Idプレイヤーのゲームセッション識別子。サーバー側で課金・ロギングに使用
X-Contract-Nonceスマートコントラクトの nonce。round_num + top_bitstring と組み合わせてオンチェーン検証
X-Datacenter-Zone実行する地理ゾーンの指定（us-east / ap-northeast など）
X-Player-Keyマウス・キーボードデバイス署名のパブリックキーハッシュ（入力正当性証明）
r = round_circuit(
    5,
    mode="custom",
    endpoint="https://cure-api.example/qpu/run",
    api_key="cure_sk_xxxx",
    extra_headers={
        "X-Session-Id":      "player-0x1a2b3c",
        "X-Contract-Nonce": "7f3e9a",
        "X-Datacenter-Zone": "ap-northeast",
        "X-Player-Key":     "sha256:4d2e...",
    },
)

Smart Contract 連携パターン

量子ビット列を「改ざん困難な乱数ソース」としてスマートコントラクトの nonce に使用する設計です。ゲーマーのデバイス（マウス・キーボード）署名と組み合わせることで、入力の正当性をオンチェーンで検証できます。

設計原則
QPU 測定結果の最頻ビット列は決定論的ではないが、再現可能な量子証明（counts ヒストグラム）が添付されるため、事後検証が可能です。round_num + bitstring + qpu_seconds のハッシュをオンチェーンに記録します。 
# サーバー側 — スマートコントラクト nonce 生成フロー（疑似コード）
import hashlib, json

def make_nonce(round_num, bitstring, qpu_seconds, session_id):
    payload = json.dumps({
        "round":   round_num,
        "bits":    bitstring,          # "0100110011111"
        "qpu_s":  qpu_seconds,
        "session": session_id,
    }, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()

# nonce をオンチェーンに記録し、ゲーム結果と照合
nonce = make_nonce(5, r["bitstring"], r["qpu_seconds"], session_id)
contract.record_round(round_num=5, nonce=nonce, events=r["events"])
デバイス署名との組み合わせ
X-Player-Key ヘッダにマウス・キーボードのデバイス公開鍵ハッシュを含めることで、「特定のデバイスが特定ラウンドをプレイした」という証明を QPU 証明書に紐づけられます。ゲーマーがデバイスを慎重に守るインセンティブが生まれます。
