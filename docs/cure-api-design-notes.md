## 1. 「EX が 0」と「EX が 1 だけ残る」現象の考察

### 1.1 仕組み（`app/cure-api/page.tsx`）

- 毎秒 `cureRate × N` 回、全 N 個（1800）のセルから **ランダムに 1 個** を選び、それが EX なら PAGE として再スポーンする。
- EX は新たに生まれない（`spawn` は PAGE のみ）→ **EX = 0 は吸収状態**。一度 0 になれば戻らない。

### 1.2 データサイエンス的に見ると：コレクター問題のテール

- 特定の EX が 1 回の抽選で選ばれる確率は 1/N、抽選は毎秒 cN 回 → **各 EX は独立にレート c（=cureRate）の指数分布で治癒**。
- 全 n 個が消えるまでの時間は n 個の指数分布の最大値：
  E[T] = H_n / c ≈ (ln n + 0.577) / c
- 既定値（n ≈ 361, c = 0.04/s）: **E[T] ≈ 162 秒**。
  - 最後の 1 個だけで平均 **1/c = 25 秒**（標準偏差も 25 秒）。
  - 2 → 1 は平均 12.5 秒、3 → 2 は 8.3 秒…と、**残りが少ないほど 1 個あたりが遅くなる**。
- つまり「EX が 1 残る」のはバグではなく、**一様ランダム抽選の必然的な長いテール**。全体の約 15% の時間を最後の 1 個が占める。

### 1.3 RPG ゲーマー的に見ると

| 観点 | 解釈 | 設計の選択肢 |
| --- | --- | --- |
| 残り HP 1 のボス | 最後の 1 体が「探しても出ない」ストレス＝ガチャの天井問題 | **天井（pity）**: EX=1 が k 秒続いたら確定治癒 |
| ドロップ率 | 治癒はハズレ抽選が大半（EX 以外を引く） | **ターゲット治癒**: EX の中からだけ抽選 → 線形に減り、テールが消える |
| イベント化 | 最後の 1 体を「レアエンカウント」として演出 | **採用済み**: EX=1 のセルをリングで強調し、tail 秒数と期待値 1/c を表示 |
| 報酬 | EX=0 達成でアンロック | **採用済み**: EX=0 で 22 アルカナ・ループバインダーが開く |

### 1.4 実装したこと

- 最後の EX セルにリングを描画、`tail`（EX=1 になってからの経過秒）と `expected ≈ 1/cureRate` を表示。
- シミュレーションの EX 数が 0 になった瞬間に、ストアの `exParameter` を 0 にする（メニューの EX スライダーと同期し、既存の「EX=0 でプレースホルダー起動」も連動）。
- `reseed cells (EX → 1)` でセルを再生成し `exParameter` を 1 に戻す。

## 2. 22 アルカナ・ループバインダー（`components/cure/ArcanaLoopBinder.tsx`）

- **11 × 2** のバインダー（0–10 / 11–21）。各マスが 1 アルカナのループ。
- 各ループは 8 ステップのミニチャート：4 つの親和性（volatility / tension / rigidity / destructive）をレンズ角度で位相回転した波形。
- タップで「キュー」→ **次の小節の頭で開始／停止**（ライブループ型のクオンタイズ）。テンポはプロジェクションエンジンの BPM。
- 下部の mix メーター＝再生中ループの現在ステップ値の平均。
- 配置：総合メニューの **左側領域**（SPIRAL EYE → プレースホルダー → バインダー → ニュース）。EX = 0 のときのみ表示。

## 4. 右側領域からの選択と分割比率（`lib/cureSplit.ts`）

- 選択セル：**API-B（脳内API）— 閉眼時の皮膚感覚・固有感覚ハプティクス出力**
- `[2, 4, 6, 7]`（計 19）を **そのまま CSS z-index として使う** 配列：

| z / 比率 | 割合 | 役割 |
| --- | --- | --- |
| 2 | 10.5% | 基礎緊張緩和（境界解体） |
| 4 | 21.1% | 縦回転グラフのズレ知覚（Cure-API 連動） |
| 6 | 31.6% | ハンドル微動へのカウンター・フィードバック |
| 7 | 36.8% | API-A（METADOGG ORACLE）最優先調整ループ |

- 同じ配列から 3 つを導出：
  1. **目次**（`CureSplitIndex`）：z-index が大きいほど手前に重なるカード。レトログリッド A/B の下部に表示。
  2. **螺旋ノイズ**：CURE 中心の周りに、比率どおりの長さで 4 分割したアルキメデス螺旋。ノイズ振幅は z に比例（z7 が最も揺れる）。目次で選ぶとその帯が強調される。
  3. **無限ループ導線**：Cure 総合メニュー → Retro Grid A（BTCUSD）→ Retro Grid B（XAUUSD）→ Oracle → Cure…。`/retro-grid?page=A|B` でページを直接指定。

> UI ラベルの「トランスジェンダー派的」は外し「境界解体」としました。性自認に関わる語をハプティクス出力のパラメーター名に付けると、§5 の商品化で要配慮情報と誤解されやすいためです。戻す場合は `lib/cureSplit.ts` の 1 行です。

## 5. パラメーターのみを商品として SNS / マッチング事業者に提供するロジック

### 5.1 原則：データではなく「パラメーター」を売る

生ログ・個人単位の値は端末外に出さず、**集計済みの分布パラメーターだけ** を API で提供する。

```
端末内（ChartUI / Cure-API）
  個人のセッション → 特徴量（テンポ、ループ選択、分割比率、EX テール時間…）
        │ 明示的オプトイン（目的・提供先・撤回方法を表示）
        ▼
集約サーバー
  コホート単位で集計（k ≥ 50 未満のコホートは破棄）
  差分プライバシーのノイズ付与（ラプラス, ε ≤ 1 / リリース）
        ▼
Parameter Pack（版管理・SHA-256 ダイジェスト付き）
        ▼
事業者 API（ライセンスキー、用途制限、監査ログ）
```

### 5.2 商品の中身（例）

| Pack | 内容 | 事業者側の用途例 |

## 6. 暗号レイヤー構想（A / B・公開鍵枠・.sol・256）について

### 6.1 現状のコードが行っていること

- `projectionBlocks` / 実験記録は **SHA-256 のハッシュチェーン**（改ざん検知用）。暗号化ではなく、秘密も保持しない。
- 「量子レベルで格納」に相当する機能はブラウザアプリでは実現できません。

### 6.2 実現可能な A/B レイヤー設計案

構想の「公開鍵にまつわるアルカナ枠を B が再処理する」は、既存の標準で素直に表現できます：

| 構想 | 対応する標準技術 |
| --- | --- |
| A = 公開側（レトログリッド #15 を公開鍵枠に） | **コミット**：アルカナ枠の状態の SHA-256 / Keccak-256 を公開 |
| B = 再処理（暗号鍵） | **リビール**：後から元データを公開し検証（commit-reveal） |
| 公開鍵から 22 アルカナ枠を派生 | **BIP-32 HD 鍵派生**：xpub から子公開鍵を誰でも導出、署名は秘密鍵保持者 B のみ（例：パス `m/22'/i`, i = 0…21） |
| ビットコインの 256 | secp256k1（256 ビット楕円曲線）＋ SHA-256。イーサリアムも同じ曲線＋ Keccak-256 |
| .sol（Solidity） | コミットの記録・検証には使える。ただし **チェーン上のデータはすべて公開** なので秘密は置けない |

### 6.3 注意点

- 独自暗号は作らない。監査済みライブラリ（例：`@noble/secp256k1`, `@scure/bip32`）を使う。
- 量子耐性：secp256k1 は将来の量子計算機（Shor）に弱い。対策は NIST の耐量子署名（ML-DSA / SLH-DSA）で、「量子レベルの格納」ではありません。
- 「レトログリッド 15（公開鍵）6 マス」の 6 マスが何を指すか（選択上限 7 のうちソース 1 を除いた 6 か、など）が決まれば、#15 を公開コミット枠として UI に組み込めます。
