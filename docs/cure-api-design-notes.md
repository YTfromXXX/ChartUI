## 1. 「EX が 0」と「EX が 1 だけ残る」現象の考察

### 1.1 仕組み（`app/cure-api/page.tsx`）

- 毎秒 `cureRate × N` 回、全 N 個（1800）のセルから **ランダムに 1 個** を選び、それが EX なら PAGE として再スポーンする。
- EX は新たに生まれない（`spawn` は PAGE のみ）→ **EX = 0 は吸収状態**。一度 0 になれば戻らない。

### 1.2 データサイエンス的に見ると：コレクター問題のテール

- 特定の EX が 1 回の抽選で選ばれる確率は 1/N、抽選は毎秒 cN 回 → **各 EX は独立にレート c（=cureRate）の指数分布で治癒**。
- 全 n 個が消えるまでの時間は n 個の指数分布の最大値：
  E[T] = H_n / c ≈ (ln n + 0.577) / c
- 既定値（n ≈ 361, c = 0.04/s）: **E[T] ≈ 162 秒**。
  - 最後の 1 個だけで平均 **1/c = 25 秒**（標準偏差も 25 秒）。
  - 2 → 1 は平均 12.5 秒、3 → 2 は 8.3 秒…と、**残りが少ないほど 1 個あたりが遅くなる**。
- つまり「EX が 1 残る」のはバグではなく、**一様ランダム抽選の必然的な長いテール**。全体の約 15% の時間を最後の 1 個が占める。

### 1.3 RPG ゲーマー的に見ると

| 観点 | 解釈 | 設計の選択肢 |
| --- | --- | --- |
| 残り HP 1 のボス | 最後の 1 体が「探しても出ない」ストレス＝ガチャの天井問題 | **天井（pity）**: EX=1 が k 秒続いたら確定治癒 |
| ドロップ率 | 治癒はハズレ抽選が大半（EX 以外を引く） | **ターゲット治癒**: EX の中からだけ抽選 → 線形に減り、テールが消える |
| イベント化 | 最後の 1 体を「レアエンカウント」として演出 | **採用済み**: EX=1 のセルをリングで強調し、tail 秒数と期待値 1/c を表示 |
| 報酬 | EX=0 達成でアンロック | **採用済み**: EX=0 で 22 アルカナ・ループバインダーが開く |

### 1.4 実装したこと

- 最後の EX セルにリングを描画、`tail`（EX=1 になってからの経過秒）と `expected ≈ 1/cureRate` を表示。
- シミュレーションの EX 数が 0 になった瞬間に、ストアの `exParameter` を 0 にする（メニューの EX スライダーと同期し、既存の「EX=0 でプレースホルダー起動」も連動）。
- `reseed cells (EX → 1)` でセルを再生成し `exParameter` を 1 に戻す。

## 6. 暗号レイヤー構想（A / B・公開鍵枠・.sol・256）について

### 6.1 現状のコードが行っていること

- `projectionBlocks` / 実験記録は **SHA-256 のハッシュチェーン**（改ざん検知用）。暗号化ではなく、秘密も保持しない。
- 「量子レベルで格納」に相当する機能はブラウザアプリでは実現できません。

### 6.2 実現可能な A/B レイヤー設計案

構想の「公開鍵にまつわるアルカナ枠を B が再処理する」は、既存の標準で素直に表現できます：

| 構想 | 対応する標準技術 |
| --- | --- |
| A = 公開側（レトログリッド #15 を公開鍵枠に） | **コミット**：アルカナ枠の状態の SHA-256 / Keccak-256 を公開 |
| B = 再処理（暗号鍵） | **リビール**：後から元データを公開し検証（commit-reveal） |
| 公開鍵から 22 アルカナ枠を派生 | **BIP-32 HD 鍵派生**：xpub から子公開鍵を誰でも導出、署名は秘密鍵保持者 B のみ（例：パス `m/22'/i`, i = 0…21） |
| ビットコインの 256 | secp256k1（256 ビット楕円曲線）＋ SHA-256。イーサリアムも同じ曲線＋ Keccak-256 |
| .sol（Solidity） | コミットの記録・検証には使える。ただし **チェーン上のデータはすべて公開** なので秘密は置けない |

### 6.3 注意点

- 独自暗号は作らない。監査済みライブラリ（例：`@noble/secp256k1`, `@scure/bip32`）を使う。
- 量子耐性：secp256k1 は将来の量子計算機（Shor）に弱い。対策は NIST の耐量子署名（ML-DSA / SLH-DSA）で、「量子レベルの格納」ではありません。
- 「レトログリッド 15（公開鍵）6 マス」の 6 マスが何を指すか（選択上限 7 のうちソース 1 を除いた 6 か、など）が決まれば、#15 を公開コミット枠として UI に組み込めます。

## 7. 奇数回帰計測とハニカム特異点（`lib/oddMeter.ts`, `components/cure/HoneycombSingularity.tsx`）

- **計測器 2 本（各 22 マス）**
  - レトログリッド 22：各マスの noise × flow。
  - スパイラルグリッド 22：Oracle API の 384 キャンディのうち上昇（UP）側を Major Arcana ごとに平均した正規化高さ（axis_height / r）。DOWN は UP の原点反転なので含めると常に 0 になる。API に繋がらない場合はアルカナ螺旋格子の位置をレンズ角度で回転させた値。
- **奇数回帰**：中心（中央値）からのズレをロバスト z（MAD）で測り、ハニカムの 6 に合わせて 1 単位 = 3 段のマスに内包する。奇数段は安定、偶数段に落ちたマスは隣の奇数段へ引かれ、空いた偶数マスを「空白の特異点」（破線）とする。
- **7 選択 = 6 銀河 + 1 特異点**：レトログリッドで選んだ 7 マスのうち CURE 中心がハニカム中央の空白特異点（∅）、残り 6 マスが螺旋銀河（腕の数・巻き・向きは両計測器の奇数ターゲットから決定）。6 + 1 = 7 で奇数に戻る。
- **Cure 移動体の拡張**：両計測器の引力（pull）を合成した場を `oddField` としてストアに保存。選択した 6 マスの pull を先頭に倍音として使い、SPIRAL EYE の軌道を固定楕円から自由曲線へ広げる。placeholder の 4 パターンが介入パターン：⚪︎ 円、◻︎ 角型、(expand) 呼吸しながら最大範囲へ、(extend) 横に最大＋倍音 2 倍。
- **EX = 0 の風船**：EX が 0 になった瞬間、球の中心で 0 → 1.00 まで膨らみ、上方へ飛んでいく。形は placeholder パターンに従う（◻︎ 角型、(extend) 横長、(expand) 大きく脈動）。
- これは探索用の独自ヒューリスティックで、統計的検定や取引シグナルではありません。

### 8.3 ポップアップ → レトログリッド A / B

- placeholder の入力欄には、パターンごとの直感・自己知覚を問う文を表示する（未選択時は「いまの直感に近い形を選んでください」）。
- パターンを選ぶと『{A} or {B}』ポップアップが開く。運動・現象・関与 Kit と 2 つの選択肢カードを表示する。
  - **A = 能動・衝突**（Hypothesis A：骨格衝突／雷, BTCUSD）→ `/retro-grid?page=A`
  - **B = 受容・包摂**（Hypothesis B：殻／真空管, XAUUSD）→ `/retro-grid?page=B`
  - 選んだ Kit 自体が骨格か表皮かはカード上に別途表示する（例：#17 骨格維持の檻は B 側だが骨格）。
- 回答はこのブラウザ内にのみ保存し、レトログリッドのバナー（「choose again ↺」で Cure に戻る）と、該当 Kit マスの「直感」バッジに使う。目次の導線と合わせて Cure → A/B → Oracle → Cure の無限ループになる。

### 8.4 注意

- 回答は直感の向き（能動か受容か）を問うもので、自認・属性の記録ではない。§5 の商品化では、この回答を個人単位で外部に出さない。とくに #5 性癖のような語を個人の属性として扱わないこと。
- #6 と #8 は実在の人物名と宗教関連の用語（「E-Meter」は商標）を含む。社外に出す製品のラベルとして使う場合は、事前に商標・表現面の確認を推奨する。

## 9. レトログリッド 22 ブロックの砂嵐（`lib/retroBlocks.ts`, `components/cure/SandstormBlock.tsx`）

- 22 マスを 11 × 2 の正方形で配置。各ブロックは 16 × 16 のレトログリッドそのもの。
- **領域とカラーリングの規則はそのまま**：HEADER 4 行・BOTTOM 2 行・SIDE MENU の階段・POP UP の残り、色は領域の色相＋seed のゆらぎ。
- **22 ブロックすべて異なる配置**：階段幅の列 `[4,6,5,8,7,9,8,10,11,12]` をブロックごとに回転（0〜9、10 番目は逆順）し、右列（奇数番）は左右反転。回転・逆順・反転では各領域のセル数が変わらないので、全ブロックが同じ割合（64 / 80 / 80 / 32 セル）を保つ。22 通りすべて異なることを検証済み。
- **砂嵐（暗号処理）**：各セルの明るさは 32bit ハッシュ（暗号ストリーム）`cipher(block, cell, tick)` で決まる。ブロック左下の 12 桁はそのティックのダイジェスト。
  - ストロボが遅い（≥ 1 秒）：前後のティックの値の間を滑らかに補間するゆるやかな揺らぎ。
  - ストロボが速い（≤ 0.11 秒）：まばらなセル（最大 14%）がティック内で位相をずらして輝き、減衰するキラキラ。ブロック全体の平均輝度は一定に保つので、広い面積の点滅にはならない。
- **experiments の時空と連動**：全ブロック共通の実験クロックが `simulationSpeed` 倍で進み、速度 0 で停止、Hypothesis B の freezeFrame でその瞬間に固定。輝きの密度は volatility（殻の応力）と最新実験のエネルギー、色味は極性（LONG＝シアン、SHORT＝ローズ）。
- **永久 Y 軸の内部構造 / 円筒状の外殻**：`Y-axis core` は平面のまま、`cylinder shell` はブロックを Y 軸まわりの円筒に巻き、回転と陰影をつける。

## 10. idlecrash（`lib/idlecrash.ts`, `components/cure/IdleCrash.tsx`）

レトログリッド上の無限ループ。16 × 16 の盤面（HEADER＝スーパーエフェクト、SIDE MENU＝ABCD のキャンディの円、POP UP＝クラッシュ倍率のチャート、右端＝No.9 ファミスカルの柱と老婆、BOTTOM＝2 つのペインの耐久度）。

1. 放置すると倍率が上がり（×1.035 / ティック、老婆の待機中は ×1.06）、両ペインの耐久度が削れる。
2. 10 ティックごとに老婆が A〜D の 4 つのポートを示す。回答するまで、両ペインは幾何学模様か `[a,b,c,d]` の複製だけを出力する（倍率が上がるほど複製が増える）。
3. 回答するとキャンディがその象限へ投げ入れられ、倍率がリセットされる。A/B は SIDE MENU、C/D は POP UP を 0.4 修復する。回答直後の 12 ティックだけ 2 つのゲームが動く。
4. どちらかのペインの耐久度が 0 になると割れる演出（セルが飛び散る、点滅なし）の後、ページ A → B（B → A）へ遷移し、次の周回が始まる。
5. スーパーエフェクト：『{ポート A}』in『{ポート B}』の一文の空欄を、毎ティックの光速取引回数・倍率・Kit・領域・エンジン名で埋める。

## 11. 「1 Issue」の解消 — GreenCardKit HydrationGate と split view

- 原因：Cure-API ストアは localStorage に保存され、同じオリジンの全タブ・フレームで共有される。`/retro-grid/split` で A と B を並べると、保存値は A と B の **合成データ**（最後に書いた方が勝つ）になり、サーバーの初期描画（既定値）とクライアントの最初の描画（合成データ）が一致し得ない。
- 対策：`GreenCardKit/HydrationGate`（`useSyncExternalStore` によるハイドレーション判定）で、サーバーとハイドレーション中は同じ中立の下地だけを描き、ハイドレーション完了後に本体を描く。ストアの読み込み前に書き込みが起きないので、保存値は失われない（zustand の `skipHydration` は読み込み前の書き込みで保存値を既定値で上書きするため採用しない）。
- 検証：合成データを再現した状態で split view → cure-api → retro-grid A を巡回し、ハイドレーション警告が 6 件 → 0 件。

## 13. ChartUI ホワイトアウト版（`/menu`）と図書館（`/lab/library`）

- **ホワイトアウト版**：白い画面（ホワイトアウトした GPU）に Window をひとつ。ヘッダーのロゴの隣に器官へのリンク（背骨・心臓・肝臓・消化器・目・鼻・皮膚・毛髪 → バインダーの各フィールド）。壁紙は赤いハチワレ猫のパターン（切り替え可）。
- **22 バインダー（11 × 2）の Form**：各 Kit にパラメーター（0–1、このブラウザに保存）と `{(source):(text)}`。カッコ内はゲームから合成した解析用テキストで、優先順は 直感（2 択の回答）＞ クイズ（計測済みの段の楔形文字）＞ 双六（出現の動詞）＞ 奇数回帰（引力）＞ ∅。
- **パーマネントナイト**：2 行の盤ではナイトは「行を移り、列を ±2」しか動けない。列の偶奇が保たれるので、偶数列と奇数列の 2 つの閉じたループを永久に巡る（完全 2D のチェス）。
- **retest（メールアドレスのシミュレーション）**：SNS アカウント ID を予約済みドメイン `whiteout.example`（RFC 2606）の架空アドレスへ変換し、受信箱に「無限ループ双六」（出現の 11 段 × 図書館の 15 プラトー、retest ごとに次の周回）が届く。
  - 7 件を超えると「ChartUI ホワイトアウト版をもう一度 retest する」。
  - `.example` / `.invalid` / `.test` 以外のアドレス＝本物とみなし、保存・送信・全文表示をせず（例：`s***@g***.com`）、Famiポートを 4 つの設計中の案件（Mente フロントエンド先行・計測解析・ゲームループ・Dual／パチスロ）に分割して Mente フロントエンドへ進む。
- **赤い人体シルエット × ホログラフィック原理**：5 つのポーズ（立ち・獣医師の触診・木のポーズ・戦士 II・ジャンプ）を 24 × 40 のグリッドに描き、境界セル（スクリーン）と内部セルを数える。情報量の上限は境界 / 4（S ≤ A/4 の見立て）。眼球はひとつ、その視点から境界へ視線を引く。
- **イベント：ソフトクリームを生成**：段数はポーズの頭身 − 1（5〜7 段）、ねじれは境界／面積比から。
- **図書館**：ドゥルーズ＝ガタリの共著 2 冊（『アンチ・オイディプス』1972、『千のプラトー』1980）を書誌情報と書き下ろしの要約で置く。『千のプラトー』の 15 のプラトーをハニカムの外を回る 15 のループ・マスに対応させる。本文の引用はしない。
- **King ＆ Queen のスロット（Mente 内、今後）**：設置時は双六のマス目に従って抑揚をつけ、金銭・オッズ・実際の賭けを持ち込まない（GreenCardKit の方針どおり）。
